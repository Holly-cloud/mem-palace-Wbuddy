# 记忆宫殿 v2 — 设计文档

> 一套面向 agent 长期记忆的结构化管理方案：Markdown 作唯一真相源，slot 作冲突键，双时态处理过期，工具只做机械判断，判断权留给你。

---

## 一、问题诊断

你自研的记忆宫殿解决了「文件膨胀」，但没有解决记忆系统的四个真问题。对照主流架构的演进路径（Letta 的三层模型、Zep/Graphiti 的时态图谱、A-MEM 的卡片链接、Mem0 的写入裁决），缺的是这几块：

| 你遇到的痛点 | 缺失的机制 | 主流方案的做法 |
|---|---|---|
| 记忆内容繁杂臃肿 | 原子性与体量约束 | Zettelkasten 一卡一事 + 正文硬上限 |
| 大量过期记忆 | 生命周期状态机 | Graphiti 的 `valid_at`/`invalid_at` 双时态 |
| 相互冲突的记忆 | 冲突键定义 + 裁决流程 | Zep 时态图谱边失效、Mem0 的 LLM judge 做 ADD/UPDATE/DELETE |
| 人工了解现状困难 | 冲突可枚举 + 全景统计 | 显式的 truth table 查询，而非「你自己翻文件」 |
| 难以维护 | 索引可重建 + 维护脚本化 | 派生索引与真相源解耦 |

**核心洞察**：这四个问题其实是**同一个问题**——记忆库缺少「结构」。没有结构，就只能靠全文检索去猜有哪些记忆、哪些还活着、哪些互斥。

## 二、整体架构

四层，自上而下：

```
L1  Agent 会话层     hermes MEMORY.md 只存索引（2200 字符内），冻结快照注入
L2  palace CLI 层    add / search / doctor / resolve / gc / stats
L3  存储层           cards/*.md（唯一真相源）+ .palace/index.db（可重建索引）
L4  治理层           TTL 过期、自动合并、冷记忆归档、断链修复（手动触发）
```

### 为什么 Markdown 是真相源，SQLite 只是索引

这是本方案最关键的一个决定，直接决定了「难以维护」能不能解决：

- **人可直接读、直接改、直接 git diff**。你在排查「agent 为什么这么说」时，能用编辑器打开那张卡看原文，而不是猜数据库里存了什么。
- **工具可弃用，数据不丢失**。SQLite 表结构会随版本变，Markdown 五年前写的还是五年前的样子。
- **索引可重建**。`.palace/index.db` 删掉，`palace reindex` 一条命令恢复。它是缓存，不是仓库。

对比：纯 SQLite 方案（Mem0 / Zep 托管版）检索更快，但你就失去了「人工了解现状」这个能力——而这正是你的核心痛点。

## 三、记忆的组织方式

### 3.1 记忆卡：一卡一事

每条记忆是一个 Markdown 文件，带 YAML frontmatter：

```markdown
---
id: mem_00042
type: preference          # 8 种类型之一
title: 偏好结论先行的技术回答
subject: user              # 关于谁/什么
predicate: reply_style    # 哪个侧面
value: 先给结论和代码，再讲原因
status: active
confidence: 0.9
importance: 0.6
valid_from: 2026-10-03    # 事实何时在现实中为真
valid_to: ""              # 何时不再为真（空 = 仍有效）
recorded_at: 2026-10-03T21:58   # 系统何时知道
ended_at: ""              # 系统何时知道它失效了
source: manual
links: [mem_00017:refines]
tags: [communication]
aliases: [回复风格, 怎么回答]    # 中文触发词，跨语言检索的桥
hits: 3
last_hit: 2026-10-03T22:00
supersedes: []
superseded_by: ""
schema: 1
---

技术问题不需要铺垫和免责声明。语义化理解用户意图，不要做关键词匹配。
```

### 3.2 八种记忆类型

类型不只是分类标签，它决定了 TTL、正文上限和重要性基线：

| 类型 | 含义 | TTL | 正文上限 | 特点 |
|---|---|---|---|---|
| `profile` | 用户是谁 | 730 天 | 600 | 几乎不衰减 |
| `preference` | 希望如何被对待 | 365 天 | 600 | 变化最频繁，需定期确认 |
| `environment` | 机器、路径、工具链 | 180 天 | 800 | 变化快 |
| `project` | 进行中的工作 | 120 天 | 1200 | 项目结束后应归档 |
| `procedure` | 怎么做 | 365 天 | 1400 | 稳定 |
| `lesson` | 踩过的坑 | 540 天 | 1200 | **最容易膨胀，也最有价值** |
| `decision` | 做了什么选择、为什么 | 365 天 | 1200 | 重要性最高 |
| `episode` | 发生过什么 | 90 天 | 900 | 流水账，应沉淀为 lesson/decision |

### 3.3 slot：冲突检测的支点

**这是整套设计的核心抽象。**

```
slot = subject + "::" + predicate
例：user::reply_language
```

含义是「关于谁」×「哪个侧面」。判定规则：

- **同一 slot + 两条 active 记忆 = 冲突**（必须处理）
- **同 subject 不同 predicate = 不冲突**（不同侧面，各自独立）
- **不同 subject = 不冲突**（不同对象）

举例说明为什么这个抽象有用：

```
user::reply_language     ← 关于「语言」，两条 active 记忆 → 冲突
user::reply_style        ← 关于「风格」，不涉及
user::verbosity          ← 关于「详略」，不涉及
```

如果不定义 slot，「用户偏好」是个大口袋，什么记忆都能塞进去，永远检测不出冲突。定义成 `(subject, predicate)` 之后，冲突检测退化成一次 `GROUP BY`——这正是让工具化、人工可审计成为可能的前提。

**实践建议**：`predicate` 用英文 snake_case 作为规范形式，再用 `aliases` 挂中文触发词。因为库内 slot 用英文保证一致性，而你的查询是中文的，`aliases` 是两者之间可人工维护的桥。

## 四、索引方式

三层索引，各司其职：

| 层 | 载体 | 用途 | 维护成本 |
|---|---|---|---|
| 全文本 | SQLite FTS5（unicode61 分词） | 中文 bigram 召回 | 自动，随写入重建 |
| 结构化 | `cards` 表字段 + slot 倒排 | 冲突检测、类型/状态过滤 | 自动 |
| 人工导航 | `maps/*.md`（MOC 索引笔记） | 你手动浏览宫殿 | 手动 |

### 检索打分：相关性与先验分离

朴素的加权求和有个致命问题：**一张「重要且新」但与查询完全无关的卡片，会靠静态权重挤进结果**。

实测中就踩到了：查询「用什么语言回复我」，一张 `project::status` 的卡片靠 importance=0.9 + recency=1.0 拿到 2.05 分，压过了真正相关的记忆。

所以改成**乘法门控**：

```
relevance = lexical + slot_exact + alias_hit + tag_hit
prior     = importance×0.8 + confidence×0.4 + recency×0.3 + reuse×0.25
gated     = (1 + prior)      若 relevance > 0     # 有证据：先验只做并列项排序
          = prior × 0.15 - 0.5   若 relevance = 0   # 无证据：重罚
score     = relevance × gated + status_penalty
```

中文检索用 **bigram**（二元组）而非单字切分。单字切分会让「用」「我」这种字命中半个语料库；bigram 无需分词器即可近似词边界。

`status_penalty` 让过期/被取代的记忆自然沉底，但**不删除**——它们仍能被 `--as-of` 或 `--include-non-active` 查到。

## 五、写入流程

```
Agent 判断某事值得长期记住
  ↓
palace add --type --title --subject --predicate --value --body [--alias ...]
  ↓
① schema 校验（必填字段、类型合法性、正文体量、状态与时间窗口一致性）
  ↓
② slot 冲突预检：查该 slot 是否已有 active 记忆
  ↓
③ 写入 cards/<type>/mem_XXXXX-<slug>.md
  ↓
④ 重建索引 + 写 audit.log
  ↓
⑤ 返回值：若有冲突，同时返回 slot_conflict 区块，含建议动作与裁决命令
```

设计要点：

- **校验只拦硬伤**（缺字段、超体量、状态与时间矛盾），软问题以 warning 返回，`--force` 可越过。
- **冲突预检在写入前**，返回值明确告知「这个 slot 已有 2 条 active 记忆，建议动作是 X，裁决命令是 Y」。Agent 可以据此向你提问，而不是默默写进去制造矛盾。
- **不做无监督的批量抽取**。`distill` 命令只从会话日志里列出候选原子记忆，归纳和入库由 Agent 显式执行。盲目批量入库正是臃肿的主要来源。

### 写入时的准入判断

不是所有对话内容都该进长期记忆。建议只在这些情况写入：

- 用户明确要求记住某事
- 反复出现的偏好（同类记忆已有 2 条以上）
- 踩坑后得出的结论（→ `lesson`）
- 项目的关键决策及理由（→ `decision`）
- 环境硬事实变化（→ `environment`）

**不要写入**：一次性任务进度、可以直接查到的信息、agent 自己推理的中间结论。

## 六、提取流程

```
Agent 遇到需要历史记忆的问题
  ↓
palace search "<自然语言查询>" [--type ...] [--as-of YYYY-MM-DD]
  ↓
① 分词：中文 bigram + 拉丁词
② 对全部卡片打分（相关性 × 先验门控）
③ 单独收集「与查询同 slot」的卡片
④ 检测冲突并生成 truth table
⑤ 按分数排序返回 top-K，同时输出冲突提示
  ↓
Agent 读卡片全文（palace show <id>）
```

`search` 的输出会**主动报告冲突**：

```
─── 冲突提示 ───
slot `user::reply_language` 有 2 条 active 记忆：
  当前推断: [mem_00006] 中文
  竞争记忆: [mem_00007] 英文  (2026-10-03T21:58)
  → 同一 slot 存在多条 active 记忆，需要裁决或标注 valid_to
```

这样 Agent 不会默默选了其中一条，而是可以反问你「你上次说中文，这次说英文，以哪个为准？」——这比自信地答错好得多。

### 时点检索

双时态字段让历史查询成为可能：

```bash
palace search "用什么语言" --as-of 2026-06-01
```

返回在当时有效的记忆，而不是现在有效的。这解决了一类长期被忽略的问题：「三个月前我到底是怎么说的？」

## 七、四个痛点的具体解法

### 7.1 臃肿

| 手段 | 机制 | 效果 |
|---|---|---|
| 正文硬上限 | 按类型设定 `body_limit`，超限报错 | 强制一卡一事 |
| 体量统计 | `stats` 显示总量/中位数/P95/最大值 | 膨胀可量化 |
| 冷记忆归档 | 长期未用且重要性低 → 移出 `cards/` | 检索集长期保持精简 |
| TTL 分级 | 类型化有效期，重要性缩放窗口 | 流水账自动沉底 |
| episode 定位 | 明确标记为「应沉淀为 lesson」 | 阻止事件记录堆积 |

正文上限超限时 `add` 会直接报错并提示「一张卡只讲一件事，请拆成多张并用 links 串联」——这是最有效的反臃肿约束。

### 7.2 冲突

- **检测**：`doctor` 枚举所有同 slot 多 active 的情况，区分 `duplicate`（digest 相同）与 `divergent`（值不同）。
- **建议**：给出建议动作 + 置信度 + 理由，但不执行。
- **裁决**：`resolve` 支持五种结局，**全部保留历史**。
- **暴露**：`search` 主动报告冲突，让 Agent 有机会反问你。

关键设计：**工具不替你判断谁对**。两条记忆都可能是对的（不同时期、不同场景），工具硬选一个比留着冲突更糟。宁可让 Agent 问一句。

### 7.3 过期

- **双时态**：`valid_from/valid_to`（现实中何时为真）+ `recorded_at/ended_at`（系统何时知道）。分开的价值：今天改了偏好，仍能回答「3 月时我认为是什么」。
- **重要性缩放窗口**：`实际 TTL = 名义 TTL × (0.7 + 0.6 × importance)`。重要项目能多撑 40%，无关紧要的环境配置早点过期。
- **过期 ≠ 删除**：状态转为 `expired`，设 `valid_to`，退出默认检索但仍可追溯。
- **expire vs supersede 区分**：前者是「我不确定了/过时了」，后者是「被更新的说法取代了」。语义不同，未来的检索行为也不同。

### 7.4 维护困难

| 障碍 | 解法 |
|---|---|
| 不知道库里有什么 | `stats` 一屏看清：类型分布、状态分布、争议 slot、高频/待复核卡片 |
| 不知道该清理什么 | `doctor` 给出结构问题 + 冲突清单 + 建议动作 |
| 怕误删 | `gc` 默认 dry-run，`--execute` 才落盘 |
| 改乱了怎么办 | git 版本化 + `audit.log` 记录每次变更 |
| 索引坏了 | `rm index.db && reindex` 即可，Markdown 才是真相 |
| 索引引用了已删记忆 | `gc` 检测失效 MOC 引用并列出 |

### 维护节奏建议

```bash
palace doctor          # 每周：看看有没有冲突
palace gc              # 每月：预演过期与归档
palace gc --execute    # 确认报告无误后执行
palace backup          # 重要变更前
```

## 九、与 hermes 集成

`~/.hermes/memories/MEMORY.md` 保持 2200 字符上限内，只放**索引与取用规则**，不放记忆内容：

```markdown
## 记忆宫殿（外部存储）

长期记忆不在本文件，在 memory-palace/ 目录。

取用规则：
1. 回答涉及用户偏好、历史决策、项目状态、环境配置前，
   先运行 `python <palace>/bin/palace.py search "<主题>"`
2. 检索输出若含「冲突提示」，必须向用户确认，不得自行选择
3. 高频事实（回复风格、语言偏好）直接记住，无需检索

高频事实：
- 回复风格：结论先行，忌铺垫免责
- 语言：中文为主，技术名词保留英文
- 详略：默认精简，忌长报告

维护：每周 doctor，每月 gc --dry-run
```

生成精简索引用 `palace export`。

这个设计延续你已有的思路（memory 只留索引），但补上了索引本身的**结构**——有 slot 概念、有状态标记、有冲突告警，所以索引不会退化成一份同样臃肿的摘要。

## 十、与主流方案的关系

本方案不是另起炉灶，而是针对「个人长期使用 + 单人维护 + 无托管」这个具体场景做的取舍：

| 来源 | 借鉴 | 本方案的取舍 |
|---|---|---|
| Letta / MemGPT | 三层记忆（常驻/归档/召回） | 保留分层，但常驻层压到索引级别 |
| Graphiti / Zep | 双时态 `valid_at`/`invalid_at` | 直接采用，是解决过期的关键 |
| A-MEM | Zettelkasten 卡片 + 链接 | 采用卡片原子性，链接简化为语义关系 |
| Mem0 | 写入时裁决 ADD/UPDATE/DELETE | 采用，但**只自动处理重复项**，真冲突交人工 |
| Mastra | 后台 observer/reflector 压缩 | 改为手动触发，符合你「维护可控」的诉求 |
| LYT / MOC | 人工索引笔记 | 采用作为人工浏览层 |
| Temporal KG | 图结构关系 | **不采用**。单agent 规模下 slot 倒排足够，图数据库运维成本不划算 |

**刻意的减法**：没有向量库、没有图数据库、没有 LLM 抽取服务。理由是单人维护场景下，这些引入的运维和调试成本远超收益。检索用 FTS5 + bigram + slot 倒排已经足够，因为记忆库规模在数千条量级——这个量级下结构化过滤比语义相似度更可靠。

## 十一、演进方向

若将来记忆量超过数万条，或需要多 agent 共享，可按以下顺序升级：

1. **加 embeddings 辅助召回**：保留 slot 与状态过滤，把 lexical 换成语义相似度。schema 不变，索引层替换即可。
2. **MOC 自动生成**：用 LLM 从卡片集合生成主题索引草稿，人工确认后写入 `maps/`。
3. **后台 consolidate**：按 Letta 的 sleep-time compute，把 `gc` 挂到定时任务。
4. **多 agent 共享**：加 scope 维度（Mem0 的 tenant 隔离思路），检索时按 scope 过滤。

注意：1 和 4 是**增量替换索引层**，`cards/` 里的 Markdown 与 slot 定义完全不用改。这是「Markdown 作真相源」这个决定的长期收益。

## 附：设计取舍速查

| 决策 | 选择 | 放弃了什么 | 为什么值得 |
|---|---|---|---|
| 存储 | Markdown 真相源 | 检索速度上限 | 可审计、可迁移，人能直接维护 |
| 冲突粒度 | subject+predicate | 细粒度语义判断 | 退化成 GROUP BY，可自动化 |
| 真冲突 | 人工裁决 | 自动化程度 | 猜错比冲突更糟 |
| 过期处理 | 标记而非删除 | 存储紧凑性 | 保留历史可追溯，误判可逆 |
| 检索 | FTS5 + slot 过滤 | 语义泛化能力 | 数千条规模下结构化过滤更准 |
| 维护 | 手动触发 | 省心程度 | 变更可预期，符合半自动诉求 |
